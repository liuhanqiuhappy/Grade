# 高优先级

## H1 部分确认后，其他班级无法暂存成绩

**问题描述**
确认粒度是「课程 + 班级」，但保存是整页整批。
`frontend/src/views/course/ScoreEntry.vue` 的 `readonly` 只看 `course.status === 'CONFIRMED'`，而课程要等**全部分组**确认才转 `CONFIRMED`；`saveAll()` 又把 `rows` 里**所有行**（含已确认班级的行）打包成一个 `entries` 提交。
`ScoreServiceImpl.saveScores` 遇到 `member.groupConfirmed == true` 直接抛 3003，事务整体回滚 → **B 班一个字都存不进去**，且报错信息指向 A 班学生，教师完全无法理解。

**影响范围**
- 一门课带 ≥2 个班级、且先确认了其中一组时，**主流程阻断**（录不进去）。
- 恰好是需求 §6-4d「其他班级不受影响」与项目背景「一位教师负责多个班级」的核心场景。
- `ScoreView` 未回传行级确认标记，前端连「哪一行锁定」都判断不了。

**修复目标**
1. `ScoreView` 增加 `groupConfirmed`（该行所属分组是否已确认）。
2. `saveScores` 对已确认分组的行**跳过而非中断**，返回 `{saved, skipped, skippedStudents[]}`；不影响同批其他行。
3. 前端按 `groupConfirmed` 锁单行输入（禁用 + `已确认 · 只读` 标记），`saveAll` 只提交未锁行；返回 `skipped > 0` 时明确提示。
4. `docs/API.md` 先更新 `PUT /scores` 的返回结构与 3003 语义（3003 不再用于批量保存，仅用于单点写操作）。

**验收标准**
- [ ] 建 2 个班（A、B）各 3 人 → 录满 A → 确认 A → 回成绩页：A 组输入框只读并显示锁定标记，B 组可编辑。
- [ ] 在 B 组录入并暂存：返回 `saved = 3`，A 组数据**未被改动**（比对 `updated_at` 与分数）。
- [ ] 直接调接口提交含已确认行的 `entries`：返回 `saved=B 行数, skipped=A 行数`，HTTP 200、`code=0`，不抛 3003。
- [ ] A 组确认后，其分数再次查询保持原值；学生端 A 组仍显示已公布、B 组显示未公布。
- [ ] 新增/更新 `ScoreServiceImplTest`：`saveScoresShouldSkipConfirmedGroupRowsAndSaveOthers` 通过；`mvn test` 全绿。

## H2 已录入成绩「清空」不落库

**问题描述**
`ScoreEntry.vue` 的「清空」把 `draft` 置空 → 提交 `score: null` → `ScoreServiceImpl.saveScores` 走 `existing.setScore(null)` + `scoreMapper.updateById(existing)`。
MyBatis-Plus 3.5.7 的 `updateById` 默认字段策略是 `NOT_NULL`，**null 字段不会进 SET 子句**；SQL 实际只更新了 `version`，接口却返回 `saved = N`。用户以为清空了，刷新后分数原样回来。

**影响范围**
- 需求 §6-4a「允许留空表示尚未录入」在**已有行上不成立**，只能在新插入时成立。
- 教师在确认前改错了分数，无法退回「未录入」，只能填 0——正好踩中需求 §5「未填」与「0 分」必须区分的点。
- 同一 bug 影响所有「置空」语义，后续功能容易复制。

**修复目标**
1. `Score` 的 `score` 字段加 `@TableField(updateStrategy = FieldStrategy.ALWAYS)`，保证 null 也进 SET，同时保留 `@Version` 乐观锁。
2. 或改用 `LambdaUpdateWrapper` 显式 `.set(Score::getScore, null)` + `.eq(version)` 手写版本条件（二选一，优先方案 1）。
3. 补单测覆盖「置空」路径。

**验收标准**
- [ ] 录 85 分 → 暂存 → 清空该行 → 暂存 → 刷新页面：该行回到 `未录入`，数据库 `score IS NULL`。
- [ ] 清空后「未录入」计数 +1，不及格计数不变（0 分才算不及格）。
- [ ] 清空后该行仍可再录入并保存成功；`version` 单调递增，无 3010 误报。
- [ ] `ScoreServiceImplTest` 新增 `saveScoresShouldPersistNullToClearScore`，`mvn test` 全绿。
- [ ] 双窗口并发下清空与改分不出现静默覆盖（仍返回 3010 并指名）。

## H3 存在已确认分组的课程可被删除/改名，已公布成绩丢失

**问题描述**
`CourseServiceImpl.update` / `delete` 只拦 `status == CONFIRMED`。课程状态要等**全部分组**确认才升级，所以「A 班已公布、B 班仍草稿」时状态还是 `DRAFT`：
- `DELETE /api/courses/{id}` 会按 `score → course_member → course` 顺序**物理删除**，已公布的 A 班成绩直接消失，学生端立刻查不到。
- `PUT` 允许改课程名/学期，已公布成绩挂到改名后的课程上，对外口径漂移。

**影响范围**
- 数据丢失 + 不可恢复，与「成绩高敏感、结果可确认」的产品定位直接冲突。
- 学生端会从「已公布」变「没有该课程」，无法解释。

**修复目标**
1. 抽出 `hasConfirmedGroup(courseId)`（`course_member.group_confirmed = 1` 存在即真）。
2. `update` / `delete` 在 `status == CONFIRMED` **或** `hasConfirmedGroup` 时统一抛 3003，message 写明「该课程已有班级确认发布」。
3. `docs/API.md` 补充该约束说明。

**验收标准**
- [ ] A 班确认、B 班草稿时：删除课程返回 3003，课程与成绩均存在；改名同样返回 3003。
- [ ] 两端都未确认的课程：删除/改名照常成功（不误伤）。
- [ ] 全部确认的课程：行为与现状一致（仍 3003）。
- [ ] `CourseServiceImplTest` 新增 `deleteShouldRejectWhenAnyGroupConfirmed`、`updateShouldRejectWhenAnyGroupConfirmed`；`mvn test` 全绿。

# 中优先级

## M1 缺少「按班级批量加入课程」（需求 §6-3b 前半）

**问题描述**
`MemberRequest` 只有 `studentIds`，没有班级维度；`CourseMembers.vue` 的选人抽屉只能逐个勾选，候选列表固定 `page=1, size=50`，超过 50 人的班级连「全部加入」都做不到。需求明确要求「既可以按班级批量加入，也可以单独加入一名学生」。

**影响范围**
- 需求条目缺口（`docs/API.md` 与实现均无 `classId` 入口）。
- 40~60 人的真实班级，教师必须点几十次；学生超过 50 人时无法操作。

**修复目标**
1. `docs/API.md` 先定：`POST /api/courses/{courseId}/members` 支持 `{classId}`（按班批量）或 `{studentIds:[]}`（点名），二者择一，二选一都传时以 `studentIds` 为准或返回 4001（明确写进文档）。
2. 后端按 `classId` 展开该班学生，已在课程中的计入 `skipped`，其余新增并按当前班级写快照（BR05）。
3. 返回结构沿用 `{added, skipped}`；按班批量时额外可返回 `classId` 便于前端回显（可选）。
4. 前端抽屉增加「整班加入（N 人）」按钮，选择班级即提交 `classId`。

**验收标准**
- [ ] 新建 60 人班级 → 「整班加入」一次成功，返回 `added = 60, skipped = 0`。
- [ ] 再次整班加入：`added = 0, skipped = 60`，不报错、不重复插入（`uk_course_student` 无冲突）。
- [ ] 部分人在课程中时：`added + skipped` 等于班级人数，成员列表无重复行。
- [ ] 按班加入后 `course_member.class_id / class_name` 为加入时快照；学生随后转班，成员列表与成绩表分组不变。
- [ ] 点名加入（原 `studentIds`）行为不变，既有单测仍绿。
- [ ] 前端候选列表支持翻页或按班加载，50 人以上可操作。

## M2 并发保护可被绕过（`expectedVersion` 传 null）

**问题描述**
`saveScores` 中，当库中该行已存在而 `expectedVersion == null` 时**直接跳过版本比较**，只靠 `@Version` 兜底；而 `@Version` 用的是刚查出来的最新版本，等于永远能更新成功。客户端只要不传版本号，就能静默覆盖他人刚保存的分数。

**影响范围**
- 需求 §6-4e 的保证只剩「前端自觉」；换实现、脚本调用、第三方客户端都会踩。
- 与 `docs/API.md` 已声明的口径（「与库中不一致即判定冲突」）不一致。

**修复目标**
1. 库中行存在且 `expectedVersion == null` → 抛 3010（并指名学生）。
2. 保持「新行传 null」的语义：`existing == null && expectedVersion == null` 仍走插入。
3. `docs/API.md` 明确「该行已存在时必须回传版本号」。
4. 前端已按 `versions[id] ?? null` 回传，无需改动，但要回归验证首次录入仍能写。

**验收标准**
- [ ] 已有分数的行提交 `expectedVersion: null`：返回 3010，分数不变。
- [ ] 新行提交 `expectedVersion: null`：插入成功，`version = 0`。
- [ ] 版本匹配：保存成功且 `version + 1`。
- [ ] 版本不匹配：3010，message 含学生姓名与学号。
- [ ] 单测覆盖上述 4 种组合；`mvn test` 全绿。

## M3 已确认分组仍可加入新成员，公布状态回退（依赖 H1）

**问题描述**
`addMembers` 只拦 `course.status == CONFIRMED`。A 班已确认、B 班草稿时，新学生仍可被加进 **A 班分组**（快照写 `class_id = A`），其 `group_confirmed = false`：
- 该组统计 `confirmed` 由 true 翻回 false，前端显示「草稿」；
- 学生端本人显示「未公布」，同组其他同学显示「已公布」；
- 该组被 `allMatch` 判定为未确认，与「确认后只读」语义冲突。
锁粒度为「人」而不是「组」，是根因。

**影响范围**
- 分组确认状态可被非确认操作回退，确认结果的稳定性无保障。
- 教师看到组状态抖动，会误以为确认被撤销。

**修复目标**
1. `addMembers` 对「目标班级分组已确认」的学生**跳过并计数**（`skipped`），不中断整批；或整批拒绝并指名（二选一，写进 `docs/API.md`，建议跳过 + 回报）。
2. 单点加入同样适用。
3. 返回结构在 `{added, skipped}` 基础上区分 `skippedConfirmed`（可选但推荐，便于前端提示原因）。

**验收标准**
- [ ] A 组已确认 → 把 A 班新学生加入课程：`added = 0`，`skippedConfirmed = 1`，A 组 `confirmed` 保持 true，学生端其余同学仍「已公布」。
- [ ] 同一批次里 B 班学生照常加入（`added` 正确），不受 A 组锁定影响。
- [ ] 未确认分组加人不受影响（回归）。
- [ ] `CourseMemberServiceImplTest` 补 2 例；`mvn test` 全绿。

## M4 学号/姓名变更不同步登录账号

**问题描述**
`StudentServiceImpl.update` 修改 `student_no` / `name` 后，只更新 `student` 表；绑定的 `sys_user.username` 仍是旧学号、`display_name` 仍是旧姓名。学生用旧学号能登录，教师按新学号找不到账号，导入同名学号时 `uk_user_username` 会让绑定逻辑走偏。

**影响范围**
- 学生登录凭据与档案不一致，属于「账号 = 学号」约定被破坏。
- `bindAccount` 的复用分支依赖 `username` 匹配，脏数据会累积。

**修复目标**
1. `update` 加 `@Transactional`；学号变更时同步 `sys_user.username`（先做唯一性校验，冲突返回 2005）。
2. 姓名变更同步 `display_name`。
3. `user_id` 为空的历史数据保持原有补绑逻辑。

**验收标准**
- [ ] 改学号后：旧学号无法登录（1001），新学号 + 原口令可登录，查到的是同一份成绩。
- [ ] 改姓名后：登录后 `displayName` 与档案一致。
- [ ] 改成已存在的学号：返回 2005，`student` 与 `sys_user` 均未变更（事务回滚）。
- [ ] `StudentServiceImplTest` 补 3 例；`mvn test` 全绿。

## M5 无修改口令入口，全班共用初始口令

**问题描述**
新建/导入学生统一用初始口令 `pass1234`，系统没有任何改密接口。知道学号即可登录查看该生成绩——与「学生只能看到本人成绩」的隐私承诺冲突（需求把成绩定性为高敏感数据）。

**影响范围**
- 账号安全整体失效；演示与验收时容易暴露。
- 需求未强制要求，但属明显风险项。

**修复目标**
1. `docs/API.md` 先加 `POST /api/identity/password`，body `{oldPassword, newPassword}`，仅登录用户可调，改自己的口令。
2. `IdentityServiceImpl` 实现：旧口令不符返回 1001；新口令长度/规则校验失败返回 4001；成功后保留会话或强制重登（二选一，推荐保留）。
3. 前端在 `AppShell` 用户区加「修改口令」入口（弹窗，两次输入校验）。
4. 可选（若课程允许）：教师重置学生口令 `POST /api/students/{id}/password/reset`，重置为初始口令。

**验收标准**
- [ ] 学生登录后改密成功；退出后用新口令可登录，旧口令返回 1001。
- [ ] 旧口令输错：1001，口令不变。
- [ ] 新口令过短/为空：4001，明确字段提示。
- [ ] 未登录调用：1002。
- [ ] 改密后 `GET /api/my/scores` 行为不变（会话/身份未错乱）。

- [ ] 两教师可各自创建同名同学期课程（依赖 L1；L1 未做则此条暂缓）。

# 低优先级

## L1 课程「名称 + 学期」全局唯一，跨教师冲突
- **问题**：`V1__init_schema.sql` 的 `uk_course_name_term (name, term)` 不含 `teacher_id`，`requireNameTermUnique` 也未按教师过滤。第二个教师建同名同学期课程被 3002 拒绝。
- **影响**：多教师场景的业务合理性；单教师演示不受影响。
- **目标**：新增 `V3__course_unique_per_teacher.sql`，删旧唯一键、建 `(teacher_id, name, term)`；`requireNameTermUnique` 加 `teacher_id` 条件。
- **验收**：两个教师可建同名同学期课程；同一教师重复创建仍返回 3002；`mvn test` 全绿。
- **注意**：只新增 `V3`，不改 `V1`。

## L2 Excel 全部行非法时抛 2006，不回失败清单
- **问题**：`StudentServiceImpl.importExcel` 用 `hasDataRow` 判定，全行非法（如学号全重复）时抛 2006「文件中没有可导入的数据行」，而不是返回 `{successCount:0, failures:[...]}`。
- **影响**：与「逐行汇报失败行」的口径不一致，教师看不到具体原因。
- **目标**：只要读到过数据行（无论合法与否）就返回 `ImportResult`；仅当整表为空/只有表头才抛 2006。
- **验收**：3 行全部学号重复 → `code=0`、`successCount=0`、`failures` 3 条且行号正确；空文件仍返回 2006。

## L3 越界访问返回 3001，与错误码表 1003 语义不符
- **问题**：`requireOwnCourse` 对他人课程抛 3001（刻意隐藏资源存在性），但 `docs/API.md` 错误码表把 1003 定义为「无权执行该操作」。
- **影响**：文档与实现语义分叉，评审时易被追问。
- **目标**：保留「按不存在处理」的实现（安全优先），在 `docs/API.md` 错误码表下加一行说明：「教师访问非本人课程统一返回 3001，不返回 1003，以避免泄露资源存在性」。
- **验收**：文档说明到位；单测注释与文档一致。

## L4 删除班级策略与需求原文有偏差
- **问题**：需求 §6-2a「删除时必须保证不破坏已有的学生与成绩数据」；实现是「班内有学生即拒删（2003）」，没有「迁出后再删」的引导路径。当前实现属于保守合规，但取消了删除能力。
- **影响**：删不掉历史班级，目录会越积越多。
- **目标**：先确认口径——(A) 维持拒删，前端提示「请先将学生转班或删除」；(B) 提供批量转班后再删的入口。
- **验收**：口径写入 `docs/API.md`；前端错误提示给出可执行下一步，而非只显示 2003。

## L6 无操作审计（背景要求，超出 §6 任务要求）

# 建议处理顺序

按「先止血、再补缺、后收敛」推进，每一项都可独立交付：

1. **H2**（S）——最小改动、影响最广，先修「清空不生效」。做完就能正确区分「未录入」与「0 分」。
2. **H1**（M）——修主流程阻断，同时落地「行级锁标记」（`ScoreView.groupConfirmed`），为 M3 铺路。**这一步做完，多班级场景才算可用。**
3. **H3**（S）——关掉数据丢失口子，做完这三项高优先级问题，系统才算「敢演示」。
4. **M1**（M）——补需求缺口（按班批量加入），验收 §6-3b。
5. **M2 + M4**（S + S）——补并发与账号一致性，改动小、收益明确，可合并为一个 PR。
6. **M3**（M）——依赖 H1 的字段，收口「确认后只读」的语义。
7. **M5**（M）——安全项，涉及新接口 + 前端弹窗，单独一个 PR。
8. **M6 / L1**（S + S）——造第二个教师 + 放开唯一键，让多教师隔离可端到端验收。**顺序上 M6 依赖 L1 的第二条验收，可反过来先做 L1。**
9. **L2 / L3 / L5**（S）——清理项，可打包成一个「杂项」PR。
10. **L4**（S）——需先确认口径，确认后再动。
